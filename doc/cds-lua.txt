                                                                       *cds-lua*
cds-lua helps Neovim plugin authors fetch data, handle failures, and
refresh the editor without repeating the same asynchronous plumbing.
Tasks let you compose a request, validation, parsing, and recovery before
starting the work. HTTP keeps transport errors separate from response
statuses. Redraw preserves the selected item when rows move, and activity
turns running work into a statusline segment.

Use the modules you need. The pure Lua list and Result helpers live in
cds-lua-fp (|cds-lua-fp|), a dependency that also supplies |cds.needs| for
checking required APIs before a plugin starts.

Requirements and setup ~
The asynchronous modules require Neovim 0.13+ with vim.async available;
HTTP also requires curl on PATH. With lazy.nvim, declare both libraries
explicitly so the vocabulary is available when cds-lua loads: >lua

  return {
    "cds-io/cds-lua",
    lazy = true,
    dependencies = { { "cds-io/cds-lua-fp", lazy = true } },
  }
<
For a plugin you distribute, put this library spec in your plugin's
dependencies. Other managers must put both libraries on the runtimepath.

Check the APIs your plugin uses before registering commands. A declaration
can live in lua/example/needs.lua; this self-contained startup check uses
the same table directly: >lua

  local ok, needs = pcall(require, "cds.needs")
  if not ok then
    vim.notify("example.nvim: install cds-io/cds-lua-fp", vim.log.levels.ERROR)
    return
  end
  local problem = needs.check("example.nvim", {
    task = { "new" },
    http = { "request", "status" },
  })
  if problem then
    vim.notify(problem, vim.log.levels.ERROR)
    return
  end
  -- Register the plugin's commands here.
<
This checks that names exist, not their signatures or behavior. Functions
keep their contracts under their names; different contracts get new names.
The check complements your plugin's tests and dependency constraints.

Values and errors ~
Result-returning functions use value or nil, err: nil in the first slot
means failure, false is a valid value, and failures should carry an error.
Task composition instead tests the error slot: a non-nil error is failure;
nil and false can both be successful Task values. Task.of_result and
Task:bind_result adapt the Result convention, so they require a non-nil
success value. Procedures such as redraw.restore return no result.

Start with the complete example under |cds.task|, then use the module
recipes below. This manual covers task, async, HTTP, redraw, activity,
datetime, and images.
The reference site https://cds-io.github.io/cds-lua/ covers every module,
including OAuth, secrets, and processes.

  Tasks ........................................................... |cds.task|
  Callback and native Task interop ............................... |cds.async|

  Preserving selection on refresh ............................... |cds.redraw|

                                                                      *cds.task*
A Task describes asynchronous work without starting it. Build a pipeline
once, add validation or recovery, then call run to start a fresh execution.
This keeps the request and its error handling together instead of spreading
them across callbacks. Tasks wrap vim.async; run returns its native handle.

Fetch JSON into a scratch buffer ~
Run this after installing the dependencies above. It fetches an example
JSON document, rejects non-200 responses, decodes the body, and displays it.
Transport errors are tables; parser errors here are strings. Normalize them
before adding context, rather than assuming every error has a message field.
>lua
  local Task = require("cds.task")
  local http = require("cds.http")

  local function parse_json(response)
    local ok, value = pcall(vim.json.decode, response.body)
    if not ok then
      return nil, "invalid JSON: " .. tostring(value)
    end
    return value
  end

  local fetch = Task.new(function()
    return http.request({ method = "GET", url = "https://httpbin.org/json" })
  end)
    :ensure(function(response) return response.status == http.status.OK end,
      function(response) return "HTTP " .. response.status end)
    :bind_result(parse_json)
    :map_err(function(err)
      local message = type(err) == "table" and err.message or tostring(err)
      return "loading example JSON: " .. message
    end)

  local run = fetch:run()
  run:on_complete(function(exception, value, err)
    -- Completion may be in a fast event; schedule editor changes.
    vim.schedule(function()
      local problem = exception or err
      if problem ~= nil then
        vim.notify(tostring(problem), vim.log.levels.ERROR)
        return
      end
      local buf = vim.api.nvim_create_buf(false, true)
      vim.api.nvim_buf_set_lines(buf, 0, -1, false,
        vim.split(vim.inspect(value), "\n", { plain = true }))
      vim.api.nvim_set_current_buf(buf)
    end)
  end)
<
The callback's first argument is the native task's exception, followed by
the Task's value and error. Task:run converts evaluation exceptions into
the returned error slot. Use async.await(run) inside asynchronous code;
run:wait(timeout_ms) is useful in synchronous scripts and tests. Both return
value, err. Keep the handle when you need to observe completion or track it
with |cds.Activity:track()|.

Choosing a composition step ~
Use map for a plain value, bind_result for value-or-error functions, and
bind when the next step returns another Task. recover returns a replacement
Task on failure; map_err only changes the error. These examples need no
network and can be run independently: >lua

  local Task = require("cds.task")
  local function positive(n)
    if n <= 0 then return nil, "expected a positive number" end
    return n
  end
  local value, err = Task.of(3)
    :map(function(n) return n * 2 end)
    :bind_result(positive)
    :bind(function(n) return Task.of("count: " .. n) end)
    :run():wait(1000)
  assert(value == "count: 6" and err == nil)

  local fallback = Task.of(-1):bind_result(positive)
    :recover(function(_) return Task.of(0) end)
    :run():wait(1000)
  assert(fallback == 0)
<
recover also catches exceptions from earlier steps; map_err transforms only
returned errors. To catch a thrown exception, use recover. When a pipeline
touches the editor before completion, put on_main before that step if an
earlier producer can resume in a fast event.

==============================================================================
                                                                     *cds.async*
Use Task for composable workflows; use cds.async when adapting a callback
API, awaiting a native handle, or sharing a semaphore. This module exports
vim.async directly with narrower types for the functions used by cds-lua.
Keeping the dependency here limits the changes needed as vim.async evolves.
It requires Neovim 0.13+ with vim.async available.

For example, suspend a task until a scheduled callback completes: >lua

  local async = require("cds.async")
  local run = async.run(function()
    async.await(1, function(done) vim.defer_fn(done, 10) end)
    return "ready"
  end)
  assert(run:wait(1000) == "ready")
<
In the callback form of await, the first argument is the position where
await inserts its completion callback into the function's arguments. In
this example it is the function's only argument. To await a native Task,
pass the handle directly: async.await(run), from inside another task.
Native async functions preserve their own return conventions; the
value-or-error convention belongs to the functions you run through them.

------------------------------------------------------------------------------
Alias ~
{cds.async.Step} `(fun(...: any): any, any)` a value, or nil and its error

------------------------------------------------------------------------------
Class ~
{cds.async}
Fields ~
{run} `(fun(fn: cds.async.Step, ...: any): vim.async.Task)` starts the step as a task
{await} `(fun(...: any): any, any)` a task, or (argc, callback-taking fn, args...)
{timeout} `(fun(ms: integer, task: vim.async.Task): any, any)` the task's answer, or an error at the deadline
{semaphore} `(fun(permits: integer): vim.async.Semaphore)`

                                                                      *cds.http*
Fetch a response without blocking Neovim's event loop. Call request
inside a Task or async.run, because the process runner awaits curl.
Transport failures (DNS, TLS, timeout, or spawning curl) return nil, err.
HTTP 404 and 500 are responses: the caller decides which statuses it accepts
before parsing the body. For example: >lua

  local Task = require("cds.task")
  local http = require("cds.http")
  local request = Task.new(function()
    return http.request({ method = "GET", url = "https://example.com/" })
  end):ensure(function(response) return response.status == http.status.OK end,
    function(response) return "HTTP " .. response.status end)

  -- Synchronous script/test; a plugin can observe run:on_complete instead.
  local response, err = request:run():wait(35000)
  if err ~= nil then
    local message = type(err) == "table" and err.message or tostring(err)
    vim.notify(message, vim.log.levels.ERROR)
  else
    print(response.body)
  end
<
The request timeout is in seconds (30 by default); wait takes milliseconds.
For a JSON GET, accept 200; a write may instead accept 201 or 204. A 201
response may contain a body; 204 has no response content. A 5xx status may
justify retrying, but retrying a write needs application-specific care.

Options travel on curl's stdin via --config -, so credentials in headers
or bodies do not appear in argv. Transfers use compression when offered,
and response.body is decoded. The config and parse helpers below support
the implementation; request is the normal entry point.

                                                                    *cds.redraw*
Refreshing a listing can move the item under the cursor. Save its stable
identity before replacing the lines, then find that identity in the new
listing. redraw does this for every window showing the buffer, so splits
can preserve different selections. If an item disappears, it restores the
old cursor position with the line clamped to the new buffer length.

Keep the selected item after sorting ~
This complete example opens a scratch listing with "Beta" selected, then
sorts it. The cursor follows Beta from line 1 to line 2: >lua

  local redraw = require("cds.redraw")
  local buf = vim.api.nvim_create_buf(false, true)
  vim.api.nvim_set_current_buf(buf)
  local items = { { id = "b", label = "Beta" }, { id = "a", label = "Alpha" } }
  local function draw()
    local lines = {}
    for i, item in ipairs(items) do lines[i] = item.label end
    vim.api.nvim_buf_set_lines(buf, 0, -1, false, lines)
  end
  draw()
  vim.api.nvim_win_set_cursor(0, { 1, 0 })
  local keep = {
    key = function(win)
      local item = items[vim.api.nvim_win_get_cursor(win)[1]]
      return item and item.id
    end,
    seek = function(win, id)
      for row, item in ipairs(items) do
        if item.id == id then
          vim.api.nvim_win_set_cursor(win, { row, 0 })
          return true
        end
      end
      return false
    end,
  }
  redraw.windows(buf, function()
    table.sort(items, function(a, b) return a.label < b.label end)
    draw()
  end, keep)
  assert(vim.api.nvim_win_get_cursor(0)[1] == 2)
<
Change items inside the draw callback: key must still see the old listing
when windows captures the selection. seek moves the cursor itself and
returns true when it finds the key. Omit keep to preserve line positions.

For text that arrives later, call places(buf, keep) before changing the
model, then restore(saved, keep) once the new text is present. windows wraps
those two calls around a synchronous draw. It returns the affected windows
so the caller can refresh related folds or sidebars.

                                                                      *cds.pick*
Select from a short list without putting window ownership, mappings and
teardown in each plugin. The caller supplies items and their presentation;
pick owns the temporary buffer and settles exactly once, including when
the user leaves or closes the window. The callback runs on the next main
loop turn, after teardown. Cancellation answers nil.

>lua
  require("cds.pick").select({ "Local", "Mainnet" }, {
    title = " Network ",
  }, function(item)
    if item then vim.notify("Selected " .. item) end
  end)
<
format_item renders an item; selectable can mark a heading as unselectable.
A single selectable item settles without opening a window. With more than
26 items all keys have the same length, so no key shadows another's prefix.
Escape and Ctrl-C cancel. Leaving the picker cancels without stealing focus.

                                                                   *cds.persist*
Read and write plugin state without owning the caller's model or save
schedule. Every operation returns a value or nil, err. Writes create parent
directories and replace the destination through a temporary file beside it,
so an encoding or write failure leaves the previous file intact.

>lua
  local persist = require("cds.persist")
  local path = vim.fn.stdpath("data") .. "/example/settings.json"
  local ok, err = persist.save_json(path, { enabled = true })
  if not ok then vim.notify(err, vim.log.levels.ERROR) end
  local settings, read_err = persist.load_json(path)
<
Missing or malformed files are errors; the plugin chooses its fallback.
JSON may decode to any JSON value, including false: callers validate their
own schema. These functions perform synchronous local file I/O.

                                                                   *cds.scratch*
Own a scratch buffer and the window displaying it. Hiding retains its
contents; wiping it invalidates the handle and the next open recreates it.
A window that has switched to another buffer is no longer owned. Reopening
an existing view focuses it instead of creating another split.

>lua
  local view = require("cds.scratch").new({
    name = "[Example Results]", filetype = "markdown",
    on_create = function(buf)
      vim.api.nvim_buf_set_lines(buf, 0, -1, false, { "Results" })
    end,
  })
  view:open({ kind = "vsplit", size = 0.5 })
  view:toggle() -- hide; a later toggle shows the same buffer
<
Content, folds and keymaps belong to the caller's hooks. on_show is also
called when the buffer is displayed by native editor commands. No global
mappings or commands are installed by a view. destroy releases the buffer
and detaches windows displaying it. Other views are independent.

------------------------------------------------------------------------------
Class ~

                                                                 *cds.companion*
Attach a sidebar to an editor window. Each owner gets its own scratch
buffer and split, even when two owners show the same document. The manager
tracks buffer changes and cursor movement, forgets a view when either
window closes, and releases its buffer and autocmds. Window-close cleanup
is deferred so it cannot interrupt the :q that triggered it.

The caller supplies meaning through accept, on_update and on_track:
>lua
  local contents = require("cds.companion").new({
    filetype = "example-contents", width = 32,
    accept = function(buf) return vim.bo[buf].filetype == "help" end,
    on_update = function(view, buf)
      vim.api.nvim_buf_set_lines(view.buf, 0, -1, false, {
        "Contents of " .. vim.api.nvim_buf_get_name(buf),
      })
    end,
  })
  contents:open(vim.api.nvim_get_current_win())
<
accept answers true for a supported buffer, false to close, or nil to
check again on the next main-loop turn (a buffer still being initialized).
A deferred answer is applied only to the same view and owner buffer.
refresh redraws after the owner's content changes; track follows its
cursor, except while the reader is in the companion. Hooks own content,
mappings and navigation; data is an independent table for each view.

Closing the last normal window of a tab leaves an empty buffer instead;
floating windows do not count as replacements. Options set through window
are restored when a window survives cleanup. A companion window switched
to an unrelated buffer is detached and never closed by later cleanup.

                                                                   *cds.command*
Declare a command's argument reader, work and presentation together.
register installs commands and optional keys; the shared boundary reports
returned errors and exceptions once. read runs at invocation, so the caller
can capture buffer identity and cursor position before asynchronous work.

>lua
  require("cds.command").register({ {
    name = "ExampleCount", desc = "Count current buffer lines", keys = { "<leader>ec" },
    read = function() return vim.api.nvim_get_current_buf() end,
    run = function(buf) return vim.api.nvim_buf_line_count(buf) end,
    present = function(count) vim.notify(tostring(count)) end,
  } })
<
run returns value, err; only a non-nil error slot means failure, so actions
returning nothing and values such as false work too. async=true runs work
as a cds Task and schedules presentation after completion. Each invocation
captures its own input. Command-specific validation and confirmation stay
in the caller. notify can route failures through a plugin's configured
notifier; otherwise vim.notify is used. Re-registering a command replaces its definition and keys.

      if vim.api.nvim_buf_is_valid(input.buf) then

                                                                  *cds.activity*
Show which operations are still running and how long they have taken,
without making a statusline poll each request. A tracker records active
runs, emits a User event when work starts or finishes, and redraws the
statusline every second while busy. Labels and event names belong to the
caller, so multiple plugins can use separate trackers.

Track a Task and display its status ~
This example uses a short delayed task, so it works without a server. It
replaces the current statusline with a file name and the activity segment;
in a plugin, expose segment() to the user's statusline configuration instead.
>lua
  local Task = require("cds.task")
  local async = require("cds.async")
  local activity = require("cds.activity").new({ autocmd = "ExampleActivity" })
  _G.example_activity = function() return activity:segment() end
  vim.o.statusline = "%f %{v:lua.example_activity()}"

  local work = Task.new(function()
    async.await(1, function(done) vim.defer_fn(done, 1500) end)
    return "done"
  end)
  local run = activity:track("refresh", "example", work:run())
  run:on_complete(function(exception, _, err)
    vim.schedule(function()
      if exception or err then
        vim.notify(tostring(exception or err), vim.log.levels.ERROR)
      end
    end)
  end)
<
track returns the same native handle and removes the entry on success or
failure. It observes completion; it does not consume or recover errors for
the caller. The segment becomes empty when all work finishes. For work
without a Task handle, pair begin(kind, label) with finish(id), including
every error path. Use the User event for other UI that needs to react to
busy-state changes.

                                                                    *cds.images*
Displays images below buffer lines through an optional image plugin.
Call place with a buffer, window, row, image URL or file path, and maximum
height. It returns a placement that you can remove with clear; clear_all
removes all placements in a buffer.

The supported backend is image.nvim. It must be installed and enabled;
this module handles its rendering calls and asynchronous image loading.
Use available() to check whether images can be displayed. Without an
available backend, place returns nil and draws nothing, so callers should
keep captions or alternative text readable without images.

Display a placeholder image ~
Run this in Neovim with image.nvim installed, configured, and enabled in
a terminal it supports. The placeholder service returns an image directly;
no JSON API request is needed. Its URL syntax is documented at
https://tools.placeholder.com/images (part of the Placeholder tools).
The remote image requires network access; a local file path works too.
>lua
  local images = require("cds.images")
  local buf = vim.api.nvim_create_buf(false, true)
  local win = vim.api.nvim_get_current_win()
  vim.api.nvim_win_set_buf(win, buf)
  vim.api.nvim_buf_set_lines(buf, 0, -1, false, {
    "Example: a 600 by 400 placeholder image",
    "Close this buffer to remove its image.",
  })

  -- Register cleanup before starting the asynchronous download.
  vim.api.nvim_create_autocmd("BufWipeout", {
    buffer = buf,
    once = true,
    callback = function() images.clear_all(buf) end,
  })
  if images.available() then
    local placement, err = images.place({
      buf = buf,
      win = win,
      row = 1,
      url = "https://via.placeholder.com/600x400.png?text=Example+image",
      max_height = 10,
    })
    if not placement and err then
      vim.notify(tostring(err), vim.log.levels.WARN)
    end
  end
<
The caption remains readable without a backend. row is 1-based and places
the image below that buffer line; max_height is measured in terminal rows.
For a remote URL, a placement means loading has started, not that the image
is already visible. To remove it earlier, pass it to images.clear().
Clearing before the download finishes also prevents rendering on arrival.
